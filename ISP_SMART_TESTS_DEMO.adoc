== 1. Core Concepts

=== 1.1 Predictive Test Selection Fundamentals

*The Problem*:

As test suites grow, running all tests on every code change becomes increasingly expensive:

* Hundreds or thousands of tests taking 10+ minutes to execute
* Most code changes only affect a small subset of tests
* Developers wait for results even when changes are localized
* CI infrastructure costs scale with test suite size

*The Smart Tests Solution*:

Instead of running all tests, Smart Tests uses AI to predict which tests are relevant to specific code changes:

. *Analyze*: Examine git diff to understand what changed
. *Predict*: Use ML models to identify affected tests
. *Select*: Run only the predicted subset
. *Learn*: Validate predictions and improve accuracy

*Key Benefits*:

[cols="30%,70%",options="header"]
|===
| Benefit
| Customer Impact

| *50-80% Faster Feedback*
| Developers get test results in minutes instead of 10-30+ minutes

| *Cost Reduction*
| Lower CI compute costs by running fewer tests

| *Maintained Quality*
| High accuracy (>90%) ensures regressions are caught

| *Scalability*
| Test suite can grow without proportional time increase

| *Developer Experience*
| Less waiting, faster iteration cycles
|===

=== 1.2 Observation Mode: Risk-Free Validation

*Concept*: Run all tests while Smart Tests creates predictions in parallel, allowing validation without risk.

*How It Works*:

[cols="50%,50%",options="header"]
|===
| What Happens in Your CI
| What Smart Tests Does

| All tests run normally
| Creates predicted subset based on code changes

| Test results recorded
| Uploads actual results to CloudBees

| Build succeeds/fails as usual
| Compares predictions vs. actual failures

| No behavior change
| Shows "what-if" analysis in UI
|===

*Why This Matters for Customers*:

* *Zero Risk*: Your CI pipeline continues unchanged
* *Proof of Value*: See actual time savings before committing
* *Accuracy Validation*: Verify predictions match your codebase patterns
* *Stakeholder Buy-In*: Show concrete data to management

*Metrics You'll See*:

. *Prediction Accuracy*: Did predicted subset include all failures?
. *Time Savings*: How much faster would predicted subset have been?
. *Confidence Score*: Smart Tests' certainty in predictions
. *Coverage Analysis*: Which tests were/weren't selected

[WARNING]
.⚠️ COMMON MISCONCEPTIONS: Observation Mode
====
*Misconception #1*: "Observation mode is just for demo purposes."

*Reality*: Observation mode is a critical production phase. Most successful deployments run observation mode for 1-2 weeks to validate predictions before enabling test selection.

---

*Misconception #2*: "In observation mode, Smart Tests doesn't do anything."

*Reality*: Smart Tests actively creates predictions, records data, and validates accuracy. You're building confidence while maintaining zero risk.

---

*Misconception #3*: "If accuracy is high in observation mode, I can skip to 100% adoption."

*Reality*: Start with non-critical branches or projects first. Gradual rollout (pilot → expand → majority → full) reduces risk and builds team confidence.

---

*Misconception #4*: "Observation mode slows down my CI."

*Reality*: Smart Tests operations (recording metadata, creating predictions) add negligible overhead (<5 seconds). Tests run at normal speed.
====

=== 5.5 Concept: Test Execution with Predictions

*What You're Learning*:

How Smart Tests creates predictions while your full test suite runs normally in observation mode.

*The Workflow - Universal Pattern*:

[source,text]
----
Step 1: Collect Tests
  pytest --collect-only -qq > all_tests.txt
  → Lists every test pytest can discover

Step 2: Get Code Changes
  git diff main...HEAD
  → Smart Tests reads this automatically

Step 3: Generate Predictions
  smart-tests subset pytest < all_tests.txt > predicted.txt
  → AI model predicts affected tests

Step 4: Run Tests (Observation Mode)
  pytest @all_tests.txt --junit-xml=results.xml
  → Run ALL tests (not just predicted subset)

Step 5: Record Everything
  smart-tests record tests pytest results.xml
  → Upload full results + predictions for comparison
----

*Why Observation Mode Matters*:

[cols="50%,50%",options="header"]
|===
| If Smart Tests Ran Predictions (Production Mode)
| With Observation Mode

| Only predicted tests run
| All tests run

| Missed predictions = missed bugs
| No risk - you see everything

| Need confidence before enabling
| Can prove accuracy with real data

| Savings immediate but scary
| Savings projected but validated
|===

*Demo App Execution*:

----
Tests Run: All 140+ (unit + integration + e2e)
Tests Predicted: ~70 (50% target, varies by change)
Tests Failed: 8-10 (from validation changes)
Observation: Did predicted subset include all failures?
----

*Your Application*:

Same workflow applies with:

* Your test discovery (`pytest -k`, markers, directories)
* Your test execution flags (coverage, parallel, etc.)
* Your CI platform's workflow syntax
* Your test count (50 or 5,000 tests)

[WARNING]
.⚠️ COMMON MISCONCEPTIONS: Test Execution & Predictions
====
*Misconception #1*: "Smart Tests replaces my tests immediately."

*Reality*: In observation mode, ALL tests run. Smart Tests creates predictions alongside your normal execution. You validate accuracy before relying on predictions.

---

*Misconception #2*: "If the predicted subset is smaller, I'm skipping important tests."

*Reality*: The predicted subset represents tests Smart Tests believes are affected by code changes. In observation mode, all tests run, so you can verify the prediction was correct.

---

*Misconception #3*: "Smart Tests changes my test code."

*Reality*: Smart Tests operates at the CI/CD level using standard pytest commands. Your test code remains completely unchanged.

---

*Misconception #4*: "Prediction accuracy must be 100% before production."

*Reality*: Target 85-95% accuracy. Even with occasional misses, the time savings outweigh the cost, and you can always run full suite for critical changes.
====

=== 7.1 The Six-Step Integration Pattern

*Universal Workflow - Works with Any CI Platform*:

[cols="10%,30%,60%",options="header"]
|===
| Step
| Command
| Purpose & Customization

| *1*
| `smart-tests record build`
| Groups related test sessions +
Use CI build ID: `--build $BUILD_ID`

| *2*
| `smart-tests record session`
| Creates test session in CloudBees +
Use `--observation` mode initially +
Specify `--test-suite` name (your choice)

| *3*
| `pytest --collect-only -qq`
| Lists all available tests +
Works with your pytest.ini configuration +
Respects markers, directory filters, etc.

| *4*
| `smart-tests subset pytest`
| Generates predicted test subset +
`--target 50%` is optional tuning +
Output is list of test node IDs

| *5*
| `pytest @subset.txt`
| Runs tests (all in observation mode) +
Add your pytest flags (--cov, -n, etc.) +
Standard pytest execution

| *6*
| `smart-tests record tests`
| Uploads results to CloudBees +
Requires JUnit XML format +
Includes predictions for comparison

    run: smart-tests record build --build ${{ github.run_id }}

  - name: Record session

  - name: Create subset
    run: smart-tests subset pytest < tests.txt > subset.txt

=== 7.2 pytest-Specific Integration Points

*Why These Patterns Work*:

Smart Tests leverages standard pytest features, requiring no test code changes.

==== Test Collection

*Concept*: pytest can list all tests without running them

[source,bash]
----
# Standard pytest feature
pytest --collect-only -qq [path/to/tests]

# Output format (one test per line)
tests/unit/test_auth.py::test_login
tests/unit/test_auth.py::TestAuthService::test_validate_token
tests/integration/test_api.py::test_create_user
----

*Your Application*:

Works with:

* Any directory structure (`tests/`, `test/`, `src/tests/`, etc.)
* pytest markers (`-m unit`, `-m smoke`, etc.)
* pytest.ini configurations (automatically respected)
* Test discovery patterns (automatically followed)

*Example Adaptations*:

----
# Collect only unit tests by marker
pytest --collect-only -qq -m unit

# Collect tests from specific directory
pytest --collect-only -qq src/tests/integration/

# Collect tests matching pattern
pytest --collect-only -qq -k "auth or login"

# Collect with pytest-xdist nodes
pytest --collect-only -qq --numprocesses=4
----

==== Test Execution from File

*Concept*: pytest can read test list from a file

[source,bash]
----
# Create test list file
echo "tests/unit/test_auth.py::test_login" > subset.txt
echo "tests/unit/test_user.py::test_create" >> subset.txt

# Run tests from file
pytest @subset.txt
----

*Your Application*:

Combine with your existing pytest flags:

----
# With coverage
pytest @subset.txt --cov=myapp --cov-report=html

# With parallel execution
pytest @subset.txt -n auto

# With custom plugins
pytest @subset.txt --html=report.html

# With markers
pytest @subset.txt -m "not slow"

# All together
pytest @subset.txt \
  --cov=myapp \
  -n 4 \
  -m "not slow" \
  --junit-xml=results.xml
----

==== JUnit XML Output

*Concept*: Smart Tests requires JUnit XML for result parsing

[source,bash]
----
# Required flag
pytest --junit-xml=results.xml

# Smart Tests compatibility setting
pytest -o junit_family=legacy --junit-xml=results.xml
----

*Why `junit_family=legacy`*:

* Smart Tests parses JUnit XML format
* Legacy format has most compatibility
* Newer formats (xunit2) may work but legacy is guaranteed

*Your Application*:

Add to existing commands:

----
# If you already have pytest.ini
[tool.pytest.ini_options]
junit_family = "legacy"

# Then just use
pytest --junit-xml=results.xml

# No need for -o flag
----
